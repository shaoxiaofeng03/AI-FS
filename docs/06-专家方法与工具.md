# 06 · 像 AI 专家一样学习：资料、工具与方法

> 你问「AI 专家和大神是怎么用资料和工具的」。这份文档拆解他们的**学习回路**，给你可直接抄的工作流、工具栈、提示词和反模式。
> 不是「他们用了什么神器」，而是「他们如何把信息变成能力，再变成作品和机会」。

---

## 1. 先拆掉一个误解

大神不是「知道更多名词」，而是**学习回路更快**：

```
问题 → 一手资料 → 最小实验 → 评测/反馈 → 输出/教学 → 下一个问题
```

普通人的回路是：

```
刷到推荐 → 收藏 → 看视频 → 感觉会了 → 下一个推荐
```

差别不在智商，在**回路是否闭合**。下面每一条方法，都是在缩短这个回路。

## 2. 大神学习的 8 个共性

| 共性 | 具体表现 | 你能怎么用 |
|---|---|---|
| 问题驱动 | 先有要做的东西，再找资料 | 每个主题先写 3 个问题 |
| 一手优先 | 官方文档/源码/论文 > 二手教程 | 80% 时间给一手资料 |
| 造最小轮子 | 手写一遍核心机制 | tool loop、BM25、RRF、限流 |
| 评测说话 | 用数字判断好坏 | 每个项目先建评测集 |
| 输出倒逼 | 写博客/分享/教别人 | 每周 1 篇，每月 1 次分享 |
| 快速丢弃 | 知道什么不学 | 明确「不学清单」 |
| 网络放大 | 社区/开源/同行 | 每周提 1 问、答 1 问 |
| 长期复利 | 卡片/笔记/决策日志 | 每天 10 分钟维护 |

## 3. 资料分层：把时间花在哪

| 层级 | 例子 | 占比 | 怎么用 |
|---|---|---|---|
| 一手 | 官方文档、Release Notes、源码、论文、标准/规范 | **70%** | 精读 + 跑通 + 记版本 |
| 二手 | 高质量博客、课程、书、会议演讲 | 25% | 带着问题看，补一手没讲清的 |
| 三手 | 短视频、营销文、二手翻译 | 5% | 只用来发现线索，不用于学习 |

### 3.1 判断资料质量的 6 个问题

1. 作者是谁？有没有实战/项目/论文？
2. 发布日期？版本是否匹配你现在用的？
3. 有没有代码/可复现实验？
4. 有没有利益相关（卖课/卖工具/软广）？
5. 结论有没有数据/引用支撑？
6. 有没有讲局限/失败案例？

> 一个资料如果只讲「优点」、不给代码、不给版本，基本可以跳过。

### 3.2 一手资料怎么读

**官方文档（4 步）**

1. **Quickstart**：先跑通最小例子，不要一上来读概念。
2. **Concepts/Architecture**：搞清核心抽象和它们的关系。
3. **API/Guides**：按你的场景读，不按目录读。
4. **Release Notes/迁移指南**：版本差异、废弃项、坑。

**源码（4 步）**

1. 从入口/自动配置进（Spring Boot 的 `AutoConfiguration`、LangChain 的 `invoke`）。
2. 跟一次请求链路，画时序图。
3. 找扩展点（Advisor、Interceptor、Callback、Tool）。
4. 改一行代码验证理解，再还原。

**论文（30 分钟法）**

1. 读摘要 + 图 + 结论（10min）：解决什么问题、怎么做、效果如何。
2. 读方法（10min）：关键公式/流程，跳过证明。
3. 读实验/局限（5min）：数据集、baseline、失败场景。
4. 写 5 行笔记 + 1 个「我能怎么用」（5min）。

> 只追 1–2 个方向（RAG/Agent 评测、上下文工程），不要泛读。

**标准/规范（MCP、JSON Schema、OAuth、OpenTelemetry）**

- 先读「为什么需要它」和「核心概念」，再读传输/安全。
- 用官方示例跑通，再读细节。
- 记录版本，规范变动快。

### 3.3 二手资料怎么用

- 课程：选 1 门，配 1 个项目；没跑完不开下一门。
- 书：1 本通读（建立框架）+ 1 本工具书（查）。
- 博客：只看有代码/数据/踩坑的；看完写 3 行笔记。
- 会议演讲：看架构图和取舍，不看营销页。

## 5. 工具栈：专家怎么用

### 5.1 AI 编程工具（2026 主流）

| 工具 | 形态 | 适合 | 专家用法 |
|---|---|---|---|
| Claude Code | CLI Agent | 大重构、跨文件、终端任务 | 给 spec + 验收标准；写 CLAUDE.md；小步 diff；跑测试；$20/月订阅是最高 ROI |
| OpenAI Codex CLI | CLI Agent | 代码生成、并行任务 | 任务拆分；review 每个 diff |
| Cursor | IDE | 日常编码、补全、对话 | 项目规则文件；选中上下文；不盲信 |
| Windsurf | IDE | 类似 Cursor | 同上 |
| Cline / Aider | 开源插件/CLI | 可控、可换模型 | 适合学习 agent 内部机制 |
| MCP Inspector | 调试工具 | 调试 MCP server | 开发 MCP 必备 |
| 通义灵码 / Trae 等 | 国内 IDE | 网络/合规 | 作为备选 |

**专家的 5 条使用纪律**

1. **先写 spec**：目标、输入输出、边界、验收标准、不许改的文件。
2. **小步 diff**：一次只改一个模块，方便 review 和回滚。
3. **必须跑测试**：让 AI 写测试，但你要看测试是否真的覆盖边界。
4. **读 diff**：不读 diff 就合并 = 埋雷。
5. **记录失败**：哪些任务 AI 做不好，形成自己的「AI 使用边界」。

**项目规则文件**（Cursor/Claude Code 都支持类似机制）：

```markdown
# AGENTS.md / CLAUDE.md
## 项目
Java 21 + Spring Boot + Spring AI；前端 Next.js + TS。
## 命令
- 构建：./mvnw -q -DskipTests package
- 测试：./mvnw test
- 前端：pnpm dev / pnpm test
## 约定
- 不要改 db/migration 下已发布的 SQL
- 新接口必须有 OpenAPI 注解 + 集成测试
- 所有外部调用必须有超时、重试、日志脱敏
## 验收
- 改动后必须跑通 `./mvnw test` 和相关前端测试
```

## 6. 用 AI 学习的 6 种模式（附提示词）

> 核心原则：**先自己思考 10 分钟，再让 AI 当对手/教练，而不是答案机。**
> 所有提示词都要求「先不给答案」「指出错误」「引用来源」，防止「看起来会了」。

### 6.1 诊断官：找出你的知识缺口

```text
你是一位 AI 应用开发面试官。我的背景：Java 后端 3 年，正在转 AI 应用/Agent 开发，
目标是 20K 岗位。请围绕【RAG 全链路】用 10 个递进问题诊断我的掌握程度。
规则：
1. 一次只问一个问题，等我回答后再问下一个；
2. 不要提前给答案；
3. 根据我的回答追问或换题；
4. 最后输出：掌握度评分（1-5）、3 个最大缺口、每个缺口的补法。
```

### 6.2 出题官：变式练习

```text
基于以下知识点，出 8 道变式题（不是原题复述）：
【知识点：混合检索、RRF、rerank、recall@k】
要求：
1. 覆盖概念、计算、场景选择、故障排查四类；
2. 先只给题目，不要给答案；
3. 我答完后，逐题批改，指出错误并给出更好的答案；
4. 最后把这 8 题整理成可复习的卡片（问题::答案）。
```

### 6.3 追问官：模拟面试（最重要）

```text
你是严格的技术面试官，只做一件事：追问。
主题：【我的 Atlas 项目 / RAG 评测 / Agent 状态图】。
规则：
1. 每次只问一个问题，等我说完再追问；
2. 最多追问 6 层，不给答案、不提示；
3. 专挑我回答里的模糊点、数字、取舍、边界；
4. 最后给：评分（1-5）、我卡住的层数、3 个改进行动。
```

### 6.4 费曼挑错官：检验是否真懂

```text
我用自己的话解释【RAG 的 recall@5 和 faithfulness】：
（粘贴我的解释）
请：
1. 指出事实错误、逻辑跳跃、遗漏的边界；
2. 按严重程度排序；
3. 给一个更准确的 3 句话版本；
4. 问我 2 个能暴露我是否真懂的问题。
```

### 6.5 代码审查官

```text
请审查以下代码（Java/Spring AI）：
（粘贴代码）
关注：正确性、边界、并发、超时/重试、幂等、安全（注入/越权）、可观测、成本。
输出：
1. 必须修的问题（按严重程度）；
2. 建议改法（给 diff 思路，不要直接重写全部）；
3. 需要补的测试用例；
4. 这段代码在面试里可能被追问的 3 个点。
```

### 6.6 资料筛选/论文精读

```text
请判断这篇资料是否值得我精读：
（链接/标题/摘要）
我的目标：Java 后端转 AI 应用/Agent，关注 RAG/Agent 工程化。
输出：
1. 作者/日期/版本可信度；
2. 解决什么问题、核心方法；
3. 有没有代码/数据/可复现；
4. 对我的价值（高/中/低）与建议读法（30 分钟/精读/跳过）；
5. 3 个我应该带着的问题。
```

### 6.7 周计划教练

```text
根据我的 22 周计划（附件）和本周数据：
- 完成率 X%，投入 Xh，commit X 天；
- 卡点：……
- 下周可用时间：……
请只给：
1. 下周 3 个可验收交付物（能运行/能演示）；
2. 每天 2 小时的具体安排（周一到周五）；
3. 要砍掉/降级的事；
4. 一个最可能失败的点和预案。
不要给泛泛的建议。
```

## 7. 专家的工作流（可直接抄）

### 7.1 每周 2 小时「研究时间」

| 时长 | 动作 |
|---|---|
| 30min 扫描 | Newsletter、GitHub Trending、Release Notes、社区热帖；只记录 3 条候选 |
| 30min 精读 | 选 1 篇一手资料/论文/源码，按 §3 方法读 |
| 45min 实验 | 写最小 demo/改一行/跑一个对比 |
| 15min 输出 | 写 3 行结论 + 1 张卡片 + 是否影响项目 |

### 7.2 每月 1 次「技术雷达」

- 列出本月新出现的框架/模型/协议。
- 每条只写：是什么、解决什么问题、成熟度、是否影响我的选型。
- **不追新**：只有影响项目/面试的才深入。

### 7.3 每季度 1 次「回炉重构」

- 回看 3 个月前的代码/文章，用新知识改一处。
- 把改前/改后写成博客，这是最好的成长证据。

### 7.4 项目驱动学习（最重要）

```
要做的功能 → 需要什么知识 → 读文档/源码 → 实现 → 评测 → 记录决策 → 输出
```

不要「先学完再做」。**做中学，学中做**，每个知识点都挂在一个真实问题上。

## 8. AI 工具使用的 4 个层次

| 层次 | 用法 | 典型行为 | 你在哪层 |
|---|---|---|---|
| L1 问答 | 问概念、查报错 | 复制粘贴 | 大多数人 |
| L2 生成 | 写代码/文章/测试 | 给 prompt，改结果 | 多数开发者 |
| L3 协作 | Agent 式完成任务 | 给 spec，review diff，跑测试 | 高手 |
| L4 系统 | 自动化工作流 | MCP/CI/多 Agent/自建工具 | 专家 |

**目标**：W10 前到 L3，W17 前摸到 L4（MCP + CI + 自动化评估）。

### 8.1 专家用 AI 的 7 个习惯

1. **上下文给足**：背景、目标、约束、示例、验收标准。
2. **让它当对手**：挑错、追问、出题、红队，而不是只给答案。
3. **要求可验证**：引用来源、跑测试、给命令、给数据。
4. **小步快跑**：一次一个任务，不搞「一句话生成整个系统」。
5. **保留判断**：架构/取舍/安全/成本必须自己拍板。
6. **记录边界**：哪些任务 AI 强/弱，形成个人手册。
7. **自动化重复**：脚手架、测试、文档、数据清洗交给 AI；思考留给自己。

### 8.2 不要做的事

- ❌ 把 AI 输出直接贴进简历/博客（事实错误）。
- ❌ 不读 diff 就合并。
- ❌ 用 AI 代替思考（面试时原形毕露）。
- ❌ 把密钥/隐私数据贴给 AI。
- ❌ 同时开 5 个 AI 工具，效率反而低。

## 9. 反模式：为什么你学了很多却没变强

| 反模式 | 症状 | 解药 |
|---|---|---|
| 收藏夹学习 | 收藏 100 篇，没读 3 篇 | 读完一篇写 3 行，再收藏 |
| 课程囤积 | 买了 5 门课，没跑完 1 门 | 一门课 + 一个项目 |
| 追新模型 | 每周换模型，项目没进展 | 模型可替换，评测集不变 |
| 只看不写 | 能看懂，写不出 | 手写核心机制 |
| 复制粘贴 | 代码跑通，问原理不会 | 关掉 AI 重写一遍 |
| 无评测 | 感觉变好了 | 先建评测集 |
| 信息过载 | 焦虑、什么都想学 | 明确不学清单 + 每周 3 个问题 |
| 只学不用 | 学完就忘 | 每个知识点挂一个项目任务 |
| 不输出 | 面试讲不清 | 每周 1 篇/每月 1 次分享 |

### 10.2 维护节奏

- 每天：3 行笔记 + 3–5 张卡片 + 1 个 commit。
- 每周：inbox 清空、周复盘、1 篇输出。
- 每月：回炉日、能力体检、技术雷达。
- 每季度：重构旧项目、更新简历/作品集。

### 10.3 卡片示例

- `Q::MCP 和 Function Calling 的区别？::Function Calling 是模型表达调用意图的协议；MCP 是工具接入标准，定义 server 如何暴露工具/资源、client 如何发现调用，解决复用与生态问题。`
- `Q::为什么 RAG 要混合检索？::向量擅长语义、BM25 擅长关键词/专有名词；RRF 融合两者，通常比单一检索更稳。`

## 11. 如何被看见（影响力是杠杆）

- **Build in Public**：每周发进度/指标/踩坑，持续 22 周。
- **开源**：文档、示例、翻译、bug fix 都算；一个高质量 PR > 十个 star。
- **分享**：公司内部分享、学习群、社区直播；讲一次 = 复习十次。
- **写深度文**：不要写「XX 入门」，写「我如何把 recall 从 0.71 提到 0.88」。
- **连接**：每周给 1 位同行留言/提问；参加 1 次线下/线上活动。
- **作品集**：GitHub 首页、个人站点、demo 视频，形成统一入口。

> 机会往往来自「别人知道你在做什么」，而不是简历投递。
